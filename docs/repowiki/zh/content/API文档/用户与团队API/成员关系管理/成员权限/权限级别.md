## 简介

本文档详细说明了系统中成员权限级别（查看者、编辑者、管理员）的定义、实现机制与访问控制逻辑。通过分析UserMembership模型、权限枚举类型、策略文件（policies）以及前端组件，全面阐述了不同权限级别对应的操作能力范围、权限校验流程、数据存储方式及用户界面表现。文档旨在为开发者和系统管理员提供清晰的权限体系理解，确保功能访问控制的安全性与一致性。

## 成员权限级别定义

系统定义了三种核心成员权限级别，用于控制用户对文档和集合的访问与操作能力：

- **查看者（Viewer）**：拥有只读权限，可查看文档内容，但无法进行编辑或管理操作。
- **编辑者（Editor）**：拥有读写权限，可在授权范围内编辑文档内容，并参与评论等协作功能。
- **管理员（Admin）**：拥有最高管理权限，除读写外，还可管理用户权限、移动、归档、删除文档或集合。

这些权限级别通过`DocumentPermission`和`CollectionPermission`枚举类型在`shared/types.ts`中统一定义，确保前后端使用一致的权限标识。

## UserMembership模型与权限存储

`UserMembership`模型是实现细粒度权限控制的核心数据结构，它表示用户对特定文档或集合的访问权限。

### 模型定义

该模型在客户端（`app/models/UserMembership.ts`）和服务器端（`server/models/UserMembership.ts`）均有定义，确保类型一致性。

- **客户端模型**：继承自`NavigableModel`，包含`permission`（权限级别）、`documentId`（文档ID）、`userId`（用户ID）、`sourceId`（源权限ID，用于继承）等字段。使用MobX进行状态管理，支持响应式更新。
- **服务器端模型**：基于Sequelize ORM，定义了数据库表`user_permissions`。`permission`字段被定义为字符串类型，其值受`DocumentPermission`和`CollectionPermission`枚举约束，确保数据完整性。

### 权限存储方式

权限信息以独立的记录形式存储在数据库中，而非作为用户或文档的直接属性。这种设计具有以下优势：
- **灵活性**：支持对单个文档或集合进行独立的权限分配。
- **继承性**：通过`sourceId`字段，子文档可以继承父文档的权限，简化权限管理。
- **可追溯性**：每条权限记录都包含`createdById`，记录了权限的创建者。

当用户被授予对某个文档的访问权限时，系统会创建一条`UserMembership`记录，明确指定该用户（`userId`）、目标文档（`documentId`）和权限级别（`permission`）。

## 权限能力矩阵

不同权限级别对应不同的操作能力范围。以下是针对文档（Document）的核心权限能力矩阵：

| 操作能力 | 查看者 (Viewer) | 编辑者 (Editor) | 管理员 (Admin) |
| :--- | :--- | :--- | :--- |
| **查看内容** | ✅ | ✅ | ✅ |
| **评论** | ✅ | ✅ | ✅ |
| **收藏/订阅** | ✅ | ✅ | ✅ |
| **导出文档** | ⚠️ (取决于团队设置) | ✅ | ✅ |
| **编辑内容** | ❌ | ✅ | ✅ |
| **分享文档** | ❌ | ✅ | ✅ |
| **管理用户权限** | ❌ | ❌ | ✅ |
| **移动/重命名** | ❌ | ✅ | ✅ |
| **归档/恢复** | ❌ | ✅ | ✅ |
| **删除/永久删除** | ❌ | ❌ | ✅ |

> **说明**：
> - `✅` 表示具备该能力。
> - `❌` 表示不具备该能力。
> - `⚠️` 表示能力受团队偏好设置影响（如`TeamPreference.ViewersCanExport`）。

此矩阵由策略文件（如`document.ts`）中的`allow`规则精确定义，并通过`usePolicy` Hook在前端动态获取。

## 权限校验逻辑与策略实现

系统的权限校验基于一个名为`cancan`的自定义策略引擎，该引擎实现了基于角色的访问控制（RBAC）模式。

### 核心组件

- **`cancan.ts`**：提供核心的`CanCan`类，包含`allow`、`can`、`cannot`和`authorize`等方法。`allow`用于定义权限规则，`can`用于检查权限，`authorize`用于在权限不足时抛出异常。
- **`utils.ts`**：提供一系列辅助函数，如`isTeamModel`（检查用户与模型是否同属一个团队）、`isTeamAdmin`（检查用户是否为团队管理员）、`and`/`or`（组合条件）等，用于构建复杂的权限条件。

### 权限校验流程

1.  **定义规则**：在策略文件（如`document.ts`）中，使用`allow`函数定义权限规则。例如，`allow(User, "update", Document, ...)`定义了用户更新文档的条件。
2.  **检查权限**：在业务逻辑中，调用`can(actor, action, target)`来检查当前用户（`actor`）是否可以对目标对象（`target`）执行特定操作（`action`）。例如，`can(user, "update", document)`。
3.  **执行操作**：如果`can`返回`true`，则允许执行操作；否则，操作被拒绝。
4.  **强制校验**：对于关键操作，使用`authorize`函数，它会在权限不足时直接抛出`AuthorizationError`，确保安全性。

### 示例：文档更新权限

```typescript
allow(User, "update", Document, (actor, document) =>
  and(
    can(actor, "read", document), // 必须有读权限
    isTeamMutable(actor), // 团队必须是可变的
    !!document?.isActive, // 文档必须是活跃的
    or(
      includesMembership(document, [DocumentPermission.ReadWrite, DocumentPermission.Admin]), // 用户在文档上的权限为读写或管理
      can(actor, "updateDocument", document?.collection), // 用户在所属集合上有更新权限
      and(!!document?.isDraft && actor.id === document?.createdById) // 是草稿且是创建者
    )
  )
);
```

此规则表明，用户要更新文档，必须满足基本条件，并且至少满足`or`括号内的一个条件。

## 前端权限显示与交互

前端通过`usePolicy` Hook和`InputSelectPermission`等组件，将后端的权限策略无缝集成到用户界面中。

### usePolicy Hook

`usePolicy`是一个自定义React Hook，用于获取指定实体（文档或集合）的权限策略。

- **功能**：它接收一个实体或实体ID作为参数，从`policies` Store中获取对应的权限对象（`abilities`）。
- **动态加载**：如果策略不存在，它会触发实体的`loadRelations()`方法，从服务器获取最新的权限信息。
- **返回值**：返回一个包含布尔值或字符串数组的对象，例如`{ read: true, update: false, manageUsers: ["membership-id-1"] }`，其中`manageUsers`返回的是有管理权限的成员ID列表。

```typescript
const can = usePolicy(document);
// can.update 为 true 或 false
```

### 权限选择组件

`InputSelectPermission`组件用于在UI中展示和选择权限级别。

- **来源**：位于`app/components/InputSelectPermission.tsx`。
- **功能**：它渲染一个下拉选择框，选项包括“仅查看”、“可编辑”和“无访问权限”。
- **国际化**：使用`react-i18next`进行多语言支持。
- **数据绑定**：`value`和`onChange`属性与父组件的状态绑定，实现权限的更新。

### 成员列表组件

`DocumentMemberList`组件展示了文档的所有成员及其权限。

- **权限显示**：为每个成员显示一个`InputMemberPermissionSelect`下拉框，其当前值为该成员的权限。
- **权限更新**：当用户更改下拉框的值时，会调用`userMemberships.create()` API，创建或更新`UserMembership`记录，从而变更权限。
- **权限控制**：下拉框的`disabled`属性由`can.manageUsers`决定，只有管理员才能修改他人权限。

```typescript
<InputMemberPermissionSelect
  onChange={async (permission) => {
    await userMemberships.create({ documentId, userId, permission });
  }}
  disabled={!can.manageUsers}
  value={membership.permission}
/>
```

## 权限变更API调用示例

权限的变更本质上是创建、更新或删除`UserMembership`记录。以下是一个通过前端代码调用API来更新用户权限的示例：

```typescript
// 假设我们有一个 userMemberships Store 和一个目标文档
const documentId = "doc-123";
const userIdToUpdate = "user-456";
const newPermission = DocumentPermission.Admin;

try {
  // 调用 Store 的 create 方法，这会向服务器发送 POST 请求
  await userMemberships.create({
    documentId: documentId,
    userId: userIdToUpdate,
    permission: newPermission,
  });

  // 操作成功，显示成功提示
  toast.success("用户权限已更新");
} catch (error) {
  // 操作失败，可能是权限不足或网络错误
  toast.error("更新用户权限失败");
}
```

此调用会触发服务器端的`userMemberships.create`路由，该路由会：
1.  验证当前用户是否有`manageUsers`权限。
2.  在数据库中创建或更新`UserMembership`记录。
3.  如果是文档权限，可能还会触发`recreateSourcedMemberships`钩子，为所有子文档创建继承的权限记录。
4.  返回成功响应，前端Store更新状态，UI随之刷新。

## 总结

本文档系统地阐述了系统的权限体系。通过`UserMembership`模型和`DocumentPermission`枚举，实现了灵活的权限数据存储。基于`cancan`策略引擎和`utils`辅助函数，构建了清晰、可维护的权限校验逻辑。前端通过`usePolicy` Hook和专用组件，将这些权限无缝地映射到用户界面，实现了动态的权限显示和安全的权限变更。整个体系确保了不同角色的用户只能执行其被授权的操作，保障了数据的安全与协作的有序性。
